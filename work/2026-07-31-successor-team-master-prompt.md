项目是一个面向 A 股研究的多智能体 AI 分析终端。它以 GitHub 上已经成熟的 TradingAgents 方案为基础，目标不是重新发明一套系统，而是在尽量保留原作者可靠实现的前提下，提升：

## 4. 贯穿全项目的数据真实性规则

### 4.1 数据字段与形状

- 外部 DataFrame 只能按列名取字段，禁止按位置切片；
- 必须显式列出 missing，区分“字段不存在”“字段为空”“字段值为零”；
- 取最新记录前先将日期转为 datetime、排序，再取记录；
- 日期查询先规整到有效交易日，只向前回溯，不能向未来填充；
- 解析失败必须拒绝该条记录并记录原因，禁止填充当前时间；
- 禁止依赖第三方接口的行序、列序、隐式类型或固定字段数量；
- 所有外部数据都要记录 source、mode、as_of、请求窗口和 warning/error。

### 4.2 注入模型前的清洗

给 LLM 的内容必须是紧凑、经过筛选的文本：

- 删除全空列、无关列、连续 NaN 和无意义空字符串；
- 由 Python 侧预先计算同比、比例、分位、变化方向等关键指标；
- 明确写出时间窗口、数据源和缺失字段；
- 不把原始 DataFrame、原始 JSON 或巨大 markdown 表格直接塞进 prompt；
- 如果数据不可用，使用明确的“数据获取失败/该项不可用/不得据此判断”的语义。

### 4.3 历史日线与实时快照

项目当前最重要的方向之一是修正“今天没有完整实时数据”的误导：

- 技术指标、VPA、VWMA 等基于 K 线的分析必须使用完整日线或明确的历史 bars；
- 实时行情只作为独立 snapshot，包含 quote_time、price、change、volume 等真实可得字段；
- 实时快照不能伪装成完整日 K，也不能直接混入历史表后计算日线指标；
- 历史日期分析不得为了“补数据”请求实时接口；
- 当前报价、昨收、历史日线、当前交易日是否收盘必须在报告中分开标注；
- 如果只能拿到昨天收盘，要标记为历史收盘数据，不得称为当前实时价；
- 如果接口只返回部分字段，报告只能使用已确认字段，缺失项显式降级。

### 4.4 失败语义

以下行为一律视为 bug：

- return 空字符串、None 或空 DataFrame，让模型自行猜；
- 把“接口失败”写成“没有风险”“数据为零”或“趋势不明但已确认”；
- 捕获异常后 pass；
- 只在日志中记录失败，却不向需要作判断的下游传播；
- 把某一个 agent 成功而其他 agent 失败，包装为整体成功；
- 把模型的推断当成供应商事实；
- 在没有资金流、新闻、基本面或 K 线的情况下给出对应方向的强结论。

- OTP 环境变量命名不一致、缺少速率限制或错误信息泄露风险；
- /v1/models/fetch 可能存在 SSRF 风险；
- backtest 端点可能缺少认证/归属校验，且存在 TypeError、sample_interval=0 无限循环风险；
- 进程级 _config 可能产生并发请求竞态。

用户此前明确表示“不用改密钥”。这意味着不得擅自轮换密钥或改动凭证配置，不意味着可以把上述代码风险写成已解决。任何安全修复先提交最小影响面方案，区分：

- 不动密钥值的代码级安全修复；
- 需要用户确认的认证/产品行为变化；
- 明确暂缓的风险和监控建议。

## 6. 代码、测试和运行环境规范

### 6.1 仓库纪律

- 先读 AGENTS.md，再读目标文件，再查所有调用点；
- 修改原路径，不建旁路实现；
- 删除替代后的死代码；
- 不动无关文件；
- 不使用 git reset --hard、git checkout --、广泛 rm 或其他破坏性命令；
- 一个 commit 只包含一个关注点；
- 不自行提交主分支，先展示完整 diff 和验证结果；
- 任何新增依赖先询问用户；
- 不在日志、报告、commit、测试输出中暴露 secrets。

### 6.2 测试优先级

优先使用仓库已有测试和容器环境。历史上可靠的 Python 路径是：

~~~text
/app/.venv/bin/python
~~~

常见验证形式：

~~~text
docker exec tradingagents-ashare /app/.venv/bin/python -m pytest -p no:cacheprovider <具体测试> -q
docker exec tradingagents-ashare /app/.venv/bin/python -m py_compile <具体文件>
~~~

不要因为宿主机缺包就宣称代码失败，也不要因为宿主机能跑就跳过容器验证。所有测试报告必须带：

- 实际命令；
- 解释器/容器；
- 原始退出码；
- 通过/失败数量；
- warning 和未覆盖项；
- 是否使用真实外部接口。

外部数据适配器必须覆盖：

1. 正常返回；
2. 超时/接口失败；
3. 返回结构异常或关键列缺失。

bug 修复必须有能在旧实现上复现问题的测试，且断言具体内容，而不是只断言对象非空。

### 6.3 外部服务限制

- 不以一次 live API 成功证明供应商稳定；
- 不在测试中写死当天价格、未来日期或易变数据；
- 对 rate limit、认证失败、超时、结构异常分别处理；
- 不循环切换模型来掩盖 402/503/不可用服务；
- 如果服务不可用，留下清晰证据并停止在合理边界；
- 真实市场分析和长期 A/B 运行不是默认验收条件，需用户允许。

## 7. 团队协作规范

### 7.1 共享工作区

所有成员共享同一个工作区，因此：

- 每次开始和结束都记录 git status --short；
- 执行者不能覆盖不属于自己的改动；
- 同一文件同一时间只能由一个人负责；
- 两个执行者必须按路径或任务隔离；
- 审查员不直接修改执行者文件；
- 发现冲突时先停止编辑，向领导报告冲突文件、来源和建议；
- agent 掉线、stale 或重新上线时，先重新查询状态和未完成任务，不根据旧印象重复编辑。

### 7.2 squad 协作

使用 squad 前先执行 squad help，以当前安装版本实际显示的命令为准。团队必须：

- 由领导建立唯一任务 ID；
- 发送任务时写清允许路径、禁止路径、测试和 gate；
- 执行者回执后再开始；
- 任务完成时发送报告和原始测试输出；
- 审查员明确发送 PASS/FAIL/BLOCKED；
- 不把“已发送消息”当成“对方已收到并执行”；
- 不因为某成员暂时 stale 就擅自接管其未确认的写入任务；
- 领导维护一份当前成员、任务状态和阻塞原因的事实列表。

如果 squad 命令不可用，退回到共享 work/ 报告和明确的领导消息，不要私自发明冲突的协作协议。

### 7.3 状态标签

统一使用：

- PLANNED：已拆解但未开始；
- IN_PROGRESS：已确认范围并正在执行；
- WAITING_USER：需要用户决定；
- WAITING_REVIEW：执行者已交付，等待独立审查；
- REWORK：审查失败，等待返工；
- BLOCKED：外部环境/权限/服务阻塞；
- READY_FOR_USER：代码和测试满足当前阶段，等待用户确认；
- DONE：用户要求的阶段目标已完成，且无未说明的关键风险。

DONE 不能只表示“函数返回了结果”。

## 8. 推荐阶段顺序

阶段可以根据当前证据调整，但默认顺序如下：

### Phase 0：基线与范围确认

- 读取所有治理文件；
- 记录分支、HEAD、脏改动、容器和测试基线；
- 将历史快照和当前事实分开；
- 列出本轮任务明确不改的内容；
- 领导向用户确认本阶段范围。

### Phase 1：保留并审查 P2A

- 确认查询解析修复仍位于正确工作区；
- 检查完整 diff 和调用链；
- 运行专门测试、chat smoke、编译检查；
- 审查员确认没有把自定义 prompt 文本误当 symbol/date；
- 用户确认前不提交。

### Phase 2：P2B 数据边界设计与最小实现

- 先做只读调用链和数据源调查；
- 输出 daily bars、realtime snapshot、indicators、VPA 的字段契约；
- 明确历史日期、当前交易日、休市日和接口失败行为；
- 取得用户对 tradingagents/ 修改的明确授权后，再实现最小改动；
- 完成正常/失败/结构异常测试和报告来源标记。

### Phase 3：P3 数据缺口传播

- 以严格失败标记为输入；
- 在 API/service 层做稳定、去重、可测试的合并；
- 验证单/双 horizon、正常报告、空缺报告和重复失败；
- 确认前端只需要消费已有字段，不扩大 UI 范围。

### Phase 4：报告与 prompt 质量

- 统一置信度和 probability 的单位/范围；
- 让数据不可用状态进入可见报告；
- 检查研究经理的证据可见性；
- 用小范围、可回滚的离线样本做 A/B；
- 在没有新证据前，不反复改 prompt 来掩盖数据问题。

### Phase 5：安全与并发风险

- 将认证降级、默认 secret、SSRF、越权、无限循环、竞态分别建任务；
- 不轮换密钥，除非用户另行授权；
- 每项修复单独测试和审查；
- 明确哪些风险暂缓，不能把暂缓写成已修复。

### Phase 6：完整回归和交接

- API、数据、报告、解析、错误降级、容器运行路径回归；
- 再次检查无敏感信息、无死代码、无无关 diff；
- 生成用户可读的变更说明、未改内容、不确定项和后续计划；
- 用户确认后才允许提交/合并。

## 9. 验收标准

阶段验收至少要回答下列问题：

### 功能正确性

- 目标场景是否可复现？
- 修复是否作用于真实调用路径，而不是测试旁路？
- 同步和流式路径是否一致？
- 中文股票名、A 股代码、日期、自定义 prompt 是否互不污染？
- 单个 agent 失败时，其余流程是否能明确降级？

### 数据正确性

- 数据来源和时间窗口是否明确？
- 当前报价是否被误称为完整日线？
- 历史数据是否按有效交易日处理？
- 缺列、空值、结构异常和接口失败是否可见？
- 技术指标是否只使用适用粒度的 bars？
- LLM 是否收到清洗后的紧凑数据，而不是原始垃圾表？

### 安全性

- 是否出现默认用户、默认 secret、越权、SSRF、无限循环、资源耗尽或密钥泄露？
- 是否将用户确认边界外的安全/认证行为改掉？
- 错误是否暴露内部路径、凭证或过多供应商细节？

### 可维护性

- 是否改了原路径并删除死代码？
- 是否有清楚的测试、日志和错误类型？
- 是否引入了不必要依赖？
- 是否能由下一团队按报告复现？
- 是否存在未解释的脏改动或无关格式化？

任何一个关键问题无法回答，都不能报告“已完成”。

## 11. 停止条件与紧急规则

收到用户“先别动代码”“暂停”“停止”“只调查”时，所有执行者立即停止写入，保留只读证据，领导汇总当前状态。

以下情形必须暂停并报告，不得靠猜测推进：

- 当前代码与交接书矛盾；
- 测试结果与实际行为矛盾；
- 外部数据没有足够时间/字段支持结论；
- 发现可能丢失、覆盖或破坏用户现有改动；
- 需要越过 tradingagents/、数据库、依赖或密钥边界；
- 方案有两个以上合理且产品影响不同的选择；
- 需要大幅改前端或改变产品性质；
- agent 身份、任务归属或消息接收状态不确定；
- 容器、供应商或模型服务持续失败，继续尝试只会制造噪声。

错误信息、供应商故障或密钥问题不能用“换一个模型”“换一个接口”无限循环掩盖。记录证据、给出最小安全替代方案，并等待决定。

## 12. 最终行为准则

你们的评价标准不是改了多少代码，也不是报告写得多长，而是：

- 是否保护了成熟上游实现；
- 是否用证据而不是猜测处理数据；
- 是否把“没有数据”准确地传到用户能看见的地方；
- 是否让 AI 知道自己的证据边界；
- 是否每项改动都能由另一名成员复核；
- 是否保留了回滚路径；
- 是否诚实区分“已验证”“推测”“未测试”和“等待用户决定”。

任何成员如果无法证明一个结论，就不要把它写成事实。任何团队如果无法证明一个修复，就不要把它写成完成。

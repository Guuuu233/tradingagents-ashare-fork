## B1 验收表 v2：**按两个失败场景拆开**

**更正：** 上一版把两条路径混成一张表，其中「`bs.login.call_count == 0`」对 connect 失败路径**不成立**——因为 **`connect` 就发生在 `bs.login()` 内部**，login 必然已被调用。混在一起会让测试提出**自相矛盾**的要求。

---

### 场景 S1：`connect` 被护栏拒绝（发生在 `bs.login()` **内部**）

| # | 断言 |
|---|---|
| S1-1 | **`bs.login.call_count == 1`**（已被调用，内部才执行 connect） |
| S1-2 | **`send_msg` 未继续执行**（零次 send——这正是本次挂死的直接触发点） |
| S1-3 | **socket 已关闭** |
| S1-4 | **`context.default_socket is None`** |
| S1-5 | 耗时**明显低于 45 秒**，**工作线程结束** |
| S1-6 | **保留原始异常类型** → 在**清理之后使用裸 `raise`** |

> **S1-6 注意**：**不要**用 `raise NewError from exc`。它虽保留因果链，但**会改变对外异常类型**，与「原始类型不变」直接冲突。

### 场景 S2：加固安装自身失败（**尚未进入** `bs.login()`）

| # | 断言 |
|---|---|
| S2-1 | **`bs.login.call_count == 0`**（这条**只属于本场景**） |
| S2-2 | **调用路径立即停止** |
| S2-3 | **可以**转换成**生产侧的加固错误**，使用 `raise ... from exc` |
| S2-4 | 测试**必须同时断言**：① 异常是**新类型**；② **`__cause__` 是原始异常** |

### 两场景通用

- 不得使用 `socket.setdefaulttimeout()`
- 不得使用全局 session 锁串行化所有请求
- 无裸 `except` / `except Exception: pass`

**不得把「原始类型不变」（S1）与「包装后保留 cause」（S2）混成同一条**——这两条要求在各自场景下都正确，混在一起则**无法同时满足**。

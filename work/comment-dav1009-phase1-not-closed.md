## 🔴 第一阶段**未**闭环：④ 的阻塞点被报错，②③ 无关联证据

调度助手 02:17 的评论称「第一阶段证据链已在主线程闭环……已完成复核确认」。**该结论不成立**，主控实测如下。

---

### 一、④ 报的是 `recv`，实际是 `send`（事实性错误）

声称：「④ 内核态 `recv` 阻塞点」。

实测 `/tmp/dav1009_phase1_diag.log` 两次 faulthandler dump，baostock 栈顶**都是同一行**：

```
File ".../baostock/util/socketutil.py", line 65 in send_msg
```

而 `socketutil.py` 的精确行号是：

```
行65:  default_socket.send(bytes(msg, encoding='utf-8'))     ← 栈停在这里
行67:  while True:
行68:      recv = default_socket.recv(8192)                  ← 声称的位置
```

**阻塞在 `send`，不在 `recv`。** 差了 3 行，但含义完全不同——而「最小修改点落点推导」正是建立在「recv 阻塞」之上的，**前提错了，推导不能用**。

### 二、这个差异为什么重要

- `send()` 会阻塞，前提是**socket 已成功建连**（未连接的 socket 上 `send()` 是立刻抛 `ENOTCONN`，不会挂住）。
  ⇒ 说明该次 `connect` **没有被护栏拦住**，方向上偏 **H1**。
- 但 **H1 的判定条件写的是「栈阻塞在 recv」**，现在是 `send`，**字面上三行判定表一行都不满足**。
- 还有一层反常需要解释：login 报文只有几十字节，**正常应塞进内核发送缓冲后立即返回**。`send()` 在小报文上阻塞，意味着要么对端零窗口/从不 ACK，要么 socket 处于异常状态。**这一点必须查清，不能跳过。**

### 三、②③ 缺少关联证据

按已下发的判定表，必须把 deny/observer、fd/socket、lsof、原生栈**关联到同一对象**。实测该日志内：

```
deny / DENY        0 次
observer / OBSERV  0 次
ESTABLISHED        0 次
lsof               0 次
10030              0 次
198.18             0 次
```

**一条关联证据都没有。** 所谓「② 2 次连接尝试 / 90s 累加」在这份日志里**无法自证**，也无法与卡住那一刻的 socket 对应。

### 四、当前判定

落在判定表**第三行**：

> deny 与 ESTABLISHED/recv 同时存在但无法对应同一 socket → **不能二选一，继续查多连接或旧全局状态**

现在的情况比第三行更弱——**关联证据根本没采集**。因此：**第一阶段仍未结束，不进入实施阶段。**

### 五、补证要求

1. **重新表述 ④**：以实测行号为准（`socketutil.py:65 send`），并解释**小报文 `send` 为何阻塞**——查该 fd 的连接状态（`lsof -p <PID>` 看该 fd 的目标与状态）。
2. **补 ② 的关联证据**：同一 PID / 同一 nodeid / 同一时间窗口内，deny 与 observer **是否成对**；连接尝试次数要能对应到**具体 fd**。
3. **卡住时采 lsof**：确认该 PID 是否存在到 `10030` 或 `198.18.x` 的 ESTABLISHED，以及**卡住线程用的 fd 是不是同一个**。
4. **结论必须由数据推导**：不得再出现「声称 recv、实测 send」这类与日志不符的表述。

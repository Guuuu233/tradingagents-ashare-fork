# 历史案例回填幂等化：无语义变化不更新时间

## 背景

发布 `e30f312c968c1e0b82cff38df6c456941eb44f86` 后，服务启动会扫描可重试的历史案例。当前生产库中存在一条 `600519.SH` 的 `eval_date_not_closed` 暂态拒绝。启动回填在行情仍不可用、结果仍为 `【数据缺失】` 时，会重新写入拒绝元数据并更新时间；因此一次没有语义变化的启动也会产生数据库写入。

这不是 DAV-998 的“暂态拒绝可重试”逻辑回退：暂态拒绝仍必须留在队列中，收盘后仍必须再次尝试。要修的是重复扫描的写入幂等性和时间戳噪音。

## 基线与边界

- 基线：`e30f312c968c1e0b82cff38df6c456941eb44f86`
- 允许修改：`tradingagents/knowledge/historical_cases.py` 与对应 `tests/` 中的最小测试文件
- 不得修改生产数据库、不得运行生产回填、不得启动或重启服务、不得部署、不得改变 `credit_weighting_enabled`
- 测试只能使用临时副本库和 mock provider；不得触达真实外部行情或模型
- 完工交给 `代码审核员` 做同一 SHA 只读审查；禁止派“独立代码审核员”

## 实现目标

1. 对仍可重试的 refusal（至少 `future_eval_date`、`eval_date_not_closed`、`calendar_unavailable`、provider unavailable 这类非终态拒绝），若本次计算得到的字段和已有持久化状态完全相同：
   - 不改 `updated_at`；
   - 不制造无意义的 ORM dirty state；
   - 不提交无语义变化的 UPDATE。
2. 若拒绝原因、拒绝代码、terminal 标志、评估日或其他持久化字段确实发生变化，仍要正常保存变化并更新时间。
3. 若行情后来可用并成功回填，仍要更新 `actual_change_pct`、`actual_outcome`、`is_error`、清理拒绝元数据，并更新时间；不能因幂等保护阻止真实状态转换。
4. 暂态拒绝仍保留在下一次回填队列中；终态拒绝仍不应被重复扫描。
5. 保持现有“数据不可用就写 `【数据缺失】`，禁止填 0 或臆造收益”的语义。

## 必须补的测试

- 首次产生暂态 refusal 后，在相同 `as_of` 和相同 mock 结果下连续执行两次：第二次仍被扫描、仍返回 `still_missing`，但 `updated_at` 不变，且拒绝元数据不重复增长。
- 暂态 refusal 的 reason/code 发生变化时：第二次必须持久化变化并更新时间。
- 评估日收盘后 mock 行情成功：案例从 pending 成功转为已回填，字段、拒绝元数据和 `updated_at` 均正确变化。
- 现有回填、终态 refusal、未来评估日跳过、数据缺失不填零等相关测试不得回退。

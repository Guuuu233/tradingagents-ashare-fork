## 4. 完整分析验收时暴露的问题（比 shrink 更靠前）

### 4.1 自定义分析提示：空转

**结论：三千字自定义提示从未进入分析师链路。**

| 位置 | 行为 |
|---|---|
| `frontend/src/pages/Settings.tsx` | UI 有「自定义分析提示」，存 **localStorage**（`ta-custom-prompt` / `tradingagents-settings`） |
| `frontend/src/components/ChatCopilotPanel.tsx` | 仅 chat 入口：`fullPrompt = user + "\n\n[分析要求] " + customPrompt` |
| `user_llm_configs` / DB | **无** custom prompt 字段 |
| `fundamentals_analyst.py` 等 | 只用内置 `tradingagents/prompts/zh.py` + 数据块 |
| 内置 prompt | **没有** 置信度上限 75、证伪条件、次新股熔断、概率 schema 等 |

因此：
- 置信度 70 **不是**违反上限，是**根本没有上限**
- 长鑫次新股熔断没触发 = 提示词没进模型
- 当日 SELL/70 = 系统原生基线，不是自定义策略

实测（`work/analysis_runs/prompt_measure.json`）：
- 基本面 system ~557 chars，human ~15.6k，**custom 关键词全 false**

### 4.2 “1.58MB 基本面报告”真相（已第三次口径对齐）

**测量对象是 `fundamentals_report` 字段本身，不是整包 report。**

| 指标 | 值 |
|---|---|
| 文件 | `work/analysis_runs/hist_fundamentals_report.md` / DB 列 |
| chars | ~1,576,391 |
| utf-8 bytes | ~1,580,031（≈1.58MB） |
| 行数 | ~53 |
| **非空白字符** | **~2,392** |
| **空白字符** | **~1,573,999** |

爆炸形态：最后一行 Markdown 表被模型用**巨量空格**撑开：

```text
| 维度         | 现状          <约 157 万空格>
```

所以：
- **不是** 50 万 token 有效中文
- **不是** ReAct 多轮工具消息累积
- **是** 单次 LLM 输出里一张表被空白填充后落库
- 下游：`research_manager` 的 `curr_situation` 会拼 `fundamentals_report`（见 `research_manager.py`），这种脏字段会污染后续节点内存检索/上下文

今日完整任务的 fundamentals 输入侧只有 ~16k chars；1.58MB 是**输出**脏数据。

相关历史 job 例：
- `b33eac3b...` / `ecbc781d...`，`trade_date=2026-04-30`，`fundamentals_report` 长度 ~1.57M

### 4.3 “开盘减 50 股”不是幻觉

来源：`imported_portfolio_positions`
- 多测试用户有 `600519.SH = 300 股 @ 1680.5`（manual 导入）
- trader 原案减 150（50%）；risk 改成分级：先减 50
- 路径：`_compose_analysis_user_context` → `user_context` → trader/risk prompt

### 4.4 分析质量现象（自定义提示未接入时的基线）
- 当日 600519：基本面偏多、新闻偏多、主力资金承认数据失败，最终仍可 SELL/高置信
- 历史 2026-04-30：曾被 429/中断；有 job completed 但 `investment_plan` / `final_trade_decision` 为空，decision=HOLD confidence=null

  `graph/setup.py` 里的 `role_llms` key 对不上，风控三方和风控总监会直接错位

#### 阶段 C 必做：把完整 resolved 提示词文本写进报告快照（不只是 hash）

阶段 B 给 `user_custom_prompts` 每行加了 `prompt_hash`，能标识"这份报告用的是哪一版提示词"，
但 `PATCH /v1/custom-prompts` 是删行重建 —— **用户一改提示词，旧版本文本就永久消失了**。

后果针对的正是本项目的最终目标（用历史日期分析结果统计校准度）：阶段 E 做 A/B、几个月后
回头算校准度时，标着 `hash=abc123` 的那批报告会查不回去 —— 只知道两批报告用的提示词不同，
不知道旧那版到底写了什么，也就无法归因"提示词的哪处改动影响了校准度"。

**解法不是建提示词历史表**，而是阶段 C 注入时把当次的**完整 resolved 文本本身**写进报告快照
（连同 hash 和长度）。这样归因是自包含的，永远不需要回头查提示词表，也不受用户后续修改影响。
6000 字符对一份本来几百 KB 的报告可以忽略。

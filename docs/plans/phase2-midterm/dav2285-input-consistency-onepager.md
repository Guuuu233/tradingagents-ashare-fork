# 输入一致性：怎样让 O / N 两臂读到同一份输入

**卡**：DAV-2285 附项（只写文档，供第二批前总控定稿）。
**适用范围**：DAV-1789 / DAV-1450 配对对照实验的 O（基线）与 N（处理臂）两套隔离实例。
**本文只描述现状与可选做法，不改任何产品代码，也不替总控做「是否允许剔除」的裁定。**

---

## 1. 现状：两臂默认读到的是两次独立抓取

两臂各自是一台独立实例、一份快照副本库，各自跑一次 `POST /v1/analyze`。
`api/main.py` 的 `_run_job_inner` 每次都会**现场调用数据源**：

```
collected_pool = graph.data_collector.collect(ticker, request.trade_date, horizons=...)
```

`data_collector.collect` 会打行情、新闻、社交数据、资金流、宏观、指数等多个源。
**N 臂是在 O 臂跑完之后才起跑的**，两次抓取之间隔着一整份分析的时间，
所以即便配的是同一套数据源、同一份只读缓存，两臂的 pool 也**不保证逐字节相同**。

落库时 `_compute_input_snapshot`（`api/main.py`）对整个 pool 做

```python
json.dumps(pool, sort_keys=True, ensure_ascii=False,
           separators=(",", ":"), default=str)   # UTF-8 → sha256
```

得到 `{hash, algo, keys, bytes, default_str_keys?}`，写在 `result_data.input_snapshot`。

**关键局限（决定了下面所有做法）**：快照只保存 hash / keys / bytes，
**不保存可用于重算的 pool 本身**。因此事后无法「拿 pool 重算一遍」，
只能拿两份报告的快照互比；字段级差异只有在上游把 pool 一起导出来时才拿得到。

## 2. 判定口径（现行，不要改）

比对工具是 `scripts/phase2/compare_input_snapshots.py`，口径已按总控 10-12 晚 v0.3 定死：

| 口径 | 内容 |
|---|---|
| 默认 | **不剔除任何字段**，直接比原始 hash；不等即「不一致」 |
| 规范化 | **只认显式逐路径白名单文件**；精确 JSON 路径，**禁子串、禁通配符** |
| 白名单自保 | 命中 `hash` / `algo` / `keys` / `bytes` 直接报错退出（否则一条 `paths:["hash"]` 就能把两份不同输入判成一致） |
| 双结果 | 原始结果与规范化结果**分别记录、分别报告**，不合并成一个结论 |
| 留痕 | 所用白名单的 sha256 必须落进运行记录（执行器 `--snapshot-whitelist`，落在 `state.json` 与 `run_report.json`） |
| 引用 | 执行器 `experiment_executor.py:RUN_IDENTITY_KEY` 的请求体字段与服务端 `result_data.experiment_run_identity` **同名不同物**，别混 |

不一致的对：**保留原尝试 + 字段级差异 + 时间，单列，不进入同输入可比主集**；
不因不一致自动追加授权或重抽。本批不一致率 =「至少一档不一致的 O/N 对数 ÷ 已完成且两档均可比对的 O/N 对数」，
**> 10% 立即停新增请求并报总控**；分母 0 记 NA。

## 3. 总控 10-20 裁定口径（本文档按此对齐）

| 字段 | 裁定 | 理由 |
|---|---|---|
| `retrieved_at` | **可剔除** | 抓取时刻，不改变任何分析输入内容。实测取值来自 `data_collector.py:806` 的 `datetime.now(timezone.utc).isoformat()`，每次抓取必变 |
| `source_hashes` | **按集合比较**，不按列表顺序 | 同一批来源的同一组哈希，顺序是抓取/遍历顺序，无语义。实测字段在 `tradingagents/dataflows/news_event_evidence.py`（新闻事件簇的来源哈希列表） |
| 资金流校验和 | **不得剔除**，属实质差异 | 资金流数值直接进分析 |
| `global_indices` 状态 | **不得剔除**，属实质差异 | 指数状态直接进宏观判断（`global_indices` 是运行期联网取的全球指数快照，缓存缺失时返回「无数据」，两种状态都属实质） |

**有实质差异的对，标「输入不一致」、单列，不进入同输入结论。**

## 4. 怎么做才真的读到同一份输入

按代价从低到高。三条正交：谁能拿到同一份**字节**、谁能拿到同一份**时刻**、谁能拿到
可重算的**原始字段**。**只有第一条是真正「同一份输入」；后两条只是「同口径」，
统计上更弱，必须在报告里写明用的是哪一种。**

### 方案 A：同一份导出 pool，两臂各导入一次（唯一真·同输入）

1. 先跑一次数据采集（任一臂、任一实例），把 `collected_pool` **原样**导出成 JSON，
   连同导出时刻的 sha256 一起落盘。
2. 两臂开跑前把这份 pool 写入各自 `DataCollector` 的实例内缓存
   （键为 `make_cache_key(ticker, trade_date, price_basis=…)`，`collect()` 命中 `self._cache`
   即返回 deepcopy，不再走 `_fetch_all`），使其**不再出网**。
3. 两臂用同一个 pool → 采集环节完全相同 → `input_snapshot.hash` 必然相同。

- **前提**：预注入要么改 `DataCollector` 增加一个导入入口，要么由 harness 直接写
  `self._cache[key]`。**两者都属改被测代码，本卡明确不改**，列为待总控与后续实现卡
  决定的事项。
- 代价：最小（一次性导出 + 一个注入点）。
- 强度：真·同输入。可直接进同输入可比主集。

### 方案 B：同一份只读缓存 + 同一时刻窗口

不导入 pool，而是保证两臂**在同一个冻结时刻**读同一份只读缓存：

1. 跑前把两套副本库的 phase2 只读缓存统一到同一份快照，逐文件记 sha256；
2. 冻结数据截止时刻，两臂都用 `trade_date = T` 且禁用任何「晚于 T」的补抓；
3. 跑完逐臂回读 pool 的 `source_hashes`，与冻结清单核对是否全部命中。

- **失败模式（必须防）**：某源缓存缺失时，采集器会**实时回源**，抓取时刻与另一臂不同 →
  pool 不同。方案 B 因此**不能保证 hash 相同**，只能保证「同源同版本」。
- 强度：同源同版本，不是同字节。差异必须逐对实测，不能假定为 0。
- 代价：中等（缓存统一 + 禁回源开关 + 逐文件 hash 清单）。

### 方案 C：只做「同口径」规范化，不追求同字节

接受两臂 pool 本就不同，退而用白名单剔除纯运行元数据后比较：

```json
{"paths": ["retrieved_at"]}
```

- 只能剔 §3 裁定可剔的那类；资金流校验和 / `global_indices` 一律留着。
- **原始结果与规范化结果分别报告**：原始不一致率与规范化后不一致率是两个数，
  不能只报后者。
- 强度：最弱。这是「差异可解释」，不是「输入相同」。
- 代价：最低（一个白名单文件）。

## 5. 推荐

**先 A，拿不到就退 B，并在报告里写明用的是 B 不是 A。**
C 不是「方案」，是所有方案下都要并报的**第二组数字**。

理由：DAV-1789 的主指标（对齐率 J/U/B、覆盖非劣）都建立在「两臂输入相同」之上。
方案 B/C 下若原始不一致率偏高，那些对会被单列，可比子集变小；
而 §2 的 10% 停批阈值正是为这件事设的。**在原始不一致率未实测前谈非劣下界没有意义。**

## 6. 已知缺口（不改 O/N 落库契约，记为缺口）

### 6.1 渲染后提示词哈希没有，只有模板解析前缀

预注册 §2 要求冻结**最终实际渲染**的提示词 sha256。现状：

- 已有的是**模板解析前缀**（`custom_prompt_snapshot` 封存的模板片段 / 模板哈希）；
- **渲染后**（模板 + 注入 + 角色上下文拼成的最终 prompt）的哈希**没有落库**。

因此「渲染后提示词哈希」**记为已知缺口**。报告须写明原话：

> 只有模板解析前缀一致，没有渲染后哈希。

不能拿前缀一致冒充渲染后一致。本卡**不改 O/N 落库契约**，补齐它是独立事项。

### 6.2 `input_snapshot` 不保存 pool，无法事后重算字段级差异

§1 已述：快照只有 hash / keys / bytes。**只有上游同时导出 pool**，
`compare_input_snapshots.py` 的逐字段 diff 才有输入；否则只剩「hash 不等」这一条信息，
无法回答「到底哪个字段不同」。方案 A 顺带解决这一点（导出的 pool 就是重算材料）。

### 6.3 快照 `keys` 是顶层键列表，不含嵌套结构

`keys` 只列 pool 顶层键。嵌套结构（`market_data_context.*` 等）的差异**不会**体现在
`keys` 里，只体现在 `hash` 里。所以「keys 相同」**不能**推出「输入相同」；
判定一律以 `hash` 为准。

## 7. 续跑口径（对接第二批）

按总控 10-20 令：

1. **开新的 state-dir，5 对全部重跑**；已有 4 份报告**保留作试跑证据、标「不计入」**。
   新旧 state-dir 不混用——`state.json` 里的 pair 终态会让执行器跳过已终态的对，
   跨目录续跑会把旧口径的结果混进新一批。
2. **O、N 两臂同时开跑**（不是先 O 后 N）。这是 §4 方案 A/B 的前提：
   同时起跑才谈得上「同一冻结时刻窗口」；串行起跑时两臂间隔可达一整份分析的时长。
3. 不在 10-20 晚上跑（当晚 B-4）；**最早 10-21 晚上，开跑前报总控**。

### 7.1 本卡新增字段在续跑时怎么落

| 字段 | 落点 | 作用 |
|---|---|---|
| `run_identity`（下发的） | `ledger.jsonl` 每行 `runs[].run_identity` | 证明「每次请求都带了身份」 |
| `run_identity_confirmed` | 同上 | 服务端是否真的承接（`require` 口径下为 false 即该对 failed 并停批） |
| `report_account` | 同上 | 回读到的报告归属账户 |
| `poll_reconnects` | 同上 | 该次轮询重连了几次 |
| `--expect-account` | 命令行 | 要核对的固定账户 `user_id` |
| `snapshot_whitelist_sha256` | `state.json` + `run_report.json` | 本次结论用的是哪份白名单 |
| `stop_reason = run_guard_failed` | `state.json`（持久） | 凭据/身份门禁不通过；粘住，需人工解除 |

**续跑时这四个字段仍在原 `ledger.jsonl` 里**（追加写，不覆盖），所以 5 对重跑后
可以直接对两个 state-dir 的账本做逐对核查。

### 7.2 开跑前必须先过的三道（否则必然白跑）

1. **凭据**：每个实例都要 `--token <名>=<token>`，否则执行器拒启
   （`instance_token_missing`）。不配 token 时服务端 `RequireUser` 会退到
   `local-default-user`，报告不属固定账户。
2. **归属**：配 `--expect-account <固定账户 user_id>`。不配则归属只记不核，
   串号要到人工看账才发现。
3. **身份回写**：当前 O/N 服务端 `AnalyzeRequest`（pydantic v2，`extra` 默认 ignore）
   会**静默丢弃** `experiment_run_identity`，因此 `--run-identity-policy` 保持默认
   `require` 时**每一对都会判 failed**。这不是执行器故障，是「服务端还没接这个字段」。
   命中后执行器**立即停批**（`run_guard_failed`，需人工或服务端变更才能解除），
   不会把 5 对 × 2 臂全烧完。
   第二批开跑前必须先确认服务端是否承接；若未承接，要么先合服务端改动，
   要么本次显式用 `--run-identity-policy off` 并在报告里写明「身份只下发未核对」。

**这三条是本卡交付里最需要总控确认的：** 在服务端承接身份之前，
`require` 口径下开跑会在第一对就停批（得到 0 条可用数据），
`off` 口径则等于放弃身份门禁。两条路都需要总控选一条，不能默认放着开跑。
